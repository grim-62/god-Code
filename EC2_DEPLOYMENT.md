# Deploy god-code on a fresh EC2 instance

This guide deploys the complete application on one Ubuntu EC2 host: React client, API, submission worker, MongoDB, Redis, and the self-hosted Judge0 service. Caddy terminates HTTPS; Docker only publishes the client to localhost. Do not follow the legacy standalone Judge0 guide in this repository for this deployment.

## Is the project ready?

The Compose stack can be deployed to one Linux host, and its application secrets are generated by `npm run docker:init-env`. This is a single-instance deployment, not a highly available or managed production architecture. Judge0 requires privileged containers and a Linux host with cgroup v1 support. Its first image build/pull is large and code execution uses significant CPU and memory.

Before accepting real users:

- Use HTTPS with a domain name. This guide uses Caddy and Let's Encrypt.
- Choose an EC2 AMI/kernel that supports the cgroup v1 mode required by Judge0 v1.13.1, then verify it on the instance before deploying.
- Set a unique production origin and keep `.env` private.
- Set up backups, monitoring, OS updates, and a plan to rebuild/redeploy images.

## 1. Prepare the EC2 instance

Recommended starting point for a low-traffic deployment:

- Ubuntu Server 22.04 LTS, x86_64. If you already launched a different Ubuntu release, do not assume it supports the cgroup v1 mode Judge0 requires; verify it in Step 2.
- At least 4 vCPU, 16 GiB RAM, and 100 GiB gp3 EBS storage. Smaller instances may work for a brief test but can run out of memory, CPU, or disk while building Judge0 or executing submissions. Increase capacity for concurrent users.
- An Elastic IP if you want the address to remain stable across instance stops.
- A DNS A record such as `app.example.com` pointing to the Elastic IP. Wait until DNS resolves before starting Caddy.

In the EC2 security group, allow only:

| Protocol | Port | Source |
| --- | ---: | --- |
| SSH | 22 | Your current public IP (`My IP`) |
| HTTP | 80 | `0.0.0.0/0` and `::/0` (Caddy certificate and redirect traffic) |
| HTTPS | 443 | `0.0.0.0/0` and `::/0` |

Do **not** create inbound rules for 8080, 5000, 2358, 27017, 6379, or 5432. Restrict SSH to your IP. Apply the same restrictions in any host firewall.

Connect using the login name shown for the AMI:

```sh
ssh -i /path/to/key.pem ubuntu@YOUR_ELASTIC_IP
```

Update the host and install Docker Engine with the Compose plugin:

```sh
sudo apt update
sudo apt upgrade -y
sudo apt install -y ca-certificates curl gnupg git
sudo install -m 0755 -d /etc/apt/keyrings
sudo curl -fsSL https://download.docker.com/linux/ubuntu/gpg \
  -o /etc/apt/keyrings/docker.asc
sudo chmod a+r /etc/apt/keyrings/docker.asc
echo "deb [arch=$(dpkg --print-architecture) signed-by=/etc/apt/keyrings/docker.asc] https://download.docker.com/linux/ubuntu $(. /etc/os-release && echo \"$VERSION_CODENAME\") stable" \
  | sudo tee /etc/apt/sources.list.d/docker.list > /dev/null
sudo apt update
sudo apt install -y docker-ce docker-ce-cli containerd.io \
  docker-buildx-plugin docker-compose-plugin
sudo systemctl enable --now docker
sudo usermod -aG docker "$USER"
```

Log out and reconnect so the Docker group change takes effect. Membership in the `docker` group grants root-equivalent access to the host. Verify:

```sh
docker --version
docker compose version
docker run --rm hello-world
```

## 2. Verify Judge0's Linux requirement

Check the host before building or starting the stack:

```sh
stat -fc %T /sys/fs/cgroup/
```

Judge0 v1.13.1's Isolate sandbox requires cgroup v1; `tmpfs` indicates the traditional cgroup v1 mount layout. If the result is `cgroup2fs`, do not proceed expecting code execution to work. On Ubuntu 22.04, you can try switching to the legacy hierarchy:

1. Edit `/etc/default/grub` and append `systemd.unified_cgroup_hierarchy=0` inside the existing `GRUB_CMDLINE_LINUX` quoted value. Preserve any existing kernel arguments.
2. Apply the change and reboot:

   ```sh
   sudo update-grub
   sudo reboot
   ```

3. Reconnect and check `stat -fc %T /sys/fs/cgroup/` again. Continue only if it reports `tmpfs` and Docker is running. If the instance/kernel cannot provide cgroup v1, select a compatible supported Linux host; do not expose a broken Judge0 deployment.

## 3. Get the application source

Clone your Git repository (replace the placeholder with its clone URL). For a private repository, use a deploy key or another approved Git credential method; do not put access tokens in the clone URL or shell history.

```sh
cd ~
git clone YOUR_REPOSITORY_CLONE_URL god-code
cd ~/god-code
```

Check the source and available disk space:

```sh
test -f compose.yaml && test -f .env.example && test -f judge0/Dockerfile
df -h /
free -h
```

Do not upload or commit your workstation's `.env`. Generate a fresh environment file on this host:

```sh
docker run --rm \
  --user "$(id -u):$(id -g)" \
  -v "$PWD:/workspace" \
  -w /workspace \
  node:22-alpine \
  node scripts/docker/init-env.js
chmod 600 .env
```

The helper creates random JWT, Judge0, PostgreSQL, and Redis secrets and sets the Judge0 API key to match its authentication token. It refuses to overwrite an existing `.env`.

## 4. Configure the production domain and local-only app port

Edit the root environment file:

```sh
nano .env
```

Set these values, replacing the domain with the exact hostname in your DNS A record:

```dotenv
HTTP_BIND_ADDRESS=127.0.0.1
HTTP_PORT=8080
CORS_ORIGIN=https://app.example.com
TRUST_PROXY_HOPS=2
```

Keep all generated secrets unchanged and private. `HTTP_BIND_ADDRESS=127.0.0.1` ensures only host-local services can reach the plain-HTTP container. `TRUST_PROXY_HOPS=2` accounts for Caddy on the host and the Nginx container; do not expose port 8080 to the Internet. Leave `DOCKER_MONGODB_URI`, `DOCKER_REDIS_URL`, and `DOCKER_JUDGE0_URL` at their Docker service defaults. Never use `localhost` for these container-to-container URLs.

Save the file and confirm its permissions:

```sh
chmod 600 .env
```

## 5. Install Caddy for HTTPS

Install Caddy from its official Debian/Ubuntu package repository:

```sh
sudo apt install -y debian-keyring debian-archive-keyring apt-transport-https curl gnupg
curl -1sLf 'https://dl.cloudsmith.io/public/caddy/stable/gpg.key' \
  | sudo gpg --dearmor -o /usr/share/keyrings/caddy-stable-archive-keyring.gpg
curl -1sLf 'https://dl.cloudsmith.io/public/caddy/stable/debian.deb.txt' \
  | sudo tee /etc/apt/sources.list.d/caddy-stable.list
sudo apt update
sudo apt install -y caddy
```

Replace the Caddy configuration with your hostname:

```sh
sudo tee /etc/caddy/Caddyfile > /dev/null <<'EOF'
app.example.com {
    encode zstd gzip
    reverse_proxy 127.0.0.1:8080
}
EOF
```

Replace `app.example.com` in the file above with your real domain. Validate and reload Caddy:

```sh
sudo caddy validate --config /etc/caddy/Caddyfile
sudo systemctl enable --now caddy
sudo systemctl reload caddy
sudo systemctl status caddy --no-pager
```

Caddy obtains and renews certificates automatically when DNS points to this instance and ports 80 and 443 are reachable. If using a host firewall, permit those ports as well.

## 6. Validate and start the application

From `~/god-code`, validate Compose configuration without printing interpolated secrets:

```sh
docker compose config --quiet
```

Build and start all services:

```sh
docker compose up --build -d
```

The first Judge0 build can take a long time and use many gigabytes of disk. Keep the SSH session open and monitor the host in another session if possible:

```sh
docker compose ps -a
docker compose logs --tail=100 api submission-worker judge0-server judge0-workers
df -h /
free -h
```

`judge0-config` is a one-shot service; it should finish successfully. The API, client, databases, and Judge0 server should remain running. Check the public HTTPS health endpoint:

```sh
curl -fsS https://app.example.com/api/health
```

It should return JSON with `"status":"ok"`. Then open `https://app.example.com`, register an account, and verify that login and the problem pages work.

To enable admin-only pages for an account you created, set that account's email in this command:

```sh
docker compose exec mongo mongosh god-code --eval \
  'db.users.updateOne({email: "you@example.com"}, {$set: {role: "admin"}})'
```

Test code execution from an authenticated account. If Run or Submit fails, inspect the API, worker, and Judge0 logs above and confirm the EC2 instance passed the cgroup check. Do not expose Judge0's port as a workaround.

## 7. Operations

Check status and logs:

```sh
docker compose ps
docker compose logs --tail=100
sudo systemctl status caddy --no-pager
```

Deploy an update from the repository:

```sh
cd ~/god-code
git pull --ff-only
docker compose up --build -d
docker compose ps
curl -fsS https://app.example.com/api/health
```

Create regular, encrypted EBS snapshots and retain them outside the instance. The simplest consistent snapshot for this single-host setup briefly stops the services:

```sh
docker compose down
```

Then, in the AWS EC2 console, create a snapshot of the instance's root EBS volume. Docker's named database volumes live on that volume by default. Wait for the snapshot to complete, then restart the services:

```sh
docker compose up -d
docker compose ps
curl -fsS https://app.example.com/api/health
```

Snapshots briefly interrupt service and are not a substitute for testing recovery. Restrict snapshot access and retention, and test restoring one to a new EBS volume/instance. For point-in-time database backups with no downtime, configure and test database-native backups to protected off-instance storage. Monitor EBS free space; Judge0 images and build layers can consume substantial disk. Keep the OS and Docker images patched, and rebuild/redeploy deliberately.

Stop services without deleting persistent data:

```sh
docker compose down
```

**Never use `docker compose down -v` for routine shutdown or upgrades.** It deletes the named database volumes. Treat `.env` and backups as secrets; keep them out of Git and restrict access. For production with meaningful user data or availability requirements, move databases to managed services and add monitoring, tested off-host backups, and a maintenance/recovery plan.

## Troubleshooting

- **Caddy cannot get a certificate:** verify the A record resolves to the EC2 Elastic IP and security group/firewall ports 80 and 443 are open.
- **Compose says a secret is missing:** check that you are running commands from the project root and that the root `.env` exists.
- **API container exits with an invalid JWT secret:** regenerate or set a unique non-placeholder `JWT_SECRET` of at least 32 characters.
- **Judge0 config exits:** check that `JUDGE0_API_KEY` equals `JUDGE0_AUTHN_TOKEN` and the generated secrets are intact.
- **Judge0 submissions fail with sandbox/cgroup errors:** verify cgroup v1 on the EC2 host. Do not treat a healthy HTTP endpoint as proof that sandbox execution works.
- **Build fails or the host becomes unresponsive:** check `df -h /` and `free -h`; increase EBS capacity or instance size and retry.
- **Do not paste `.env`, private keys, or unredacted logs into support requests.**
